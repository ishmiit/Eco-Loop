## 1 — Title

**Eco-Loop Building Agents**
Autonomous closed-loop building control: EnergyPlus as the building, a local
open-source LLM as the brain.

One line under the title, the whole thesis:

> Telemetry leaves a running EnergyPlus simulation, an LLM reasons about it, and
> the set-points it chooses are written back into the *same* running simulation —
> no file round-trip, no restart.

Visual: the loop diagram from `docs/ARCHITECTURE.md` §1.

## 2 — The problem, made specific

Buildings are ~40% of global energy. Rule-based BMS schedules cannot react to
weather, occupancy or grid conditions.

Do not stop at the generic framing — name the building:

* Three-zone FSSAI-licensed food premises, Chennai (hot-humid).
* 240 m², uninsulated RCC roof, 230 mm brick — representative Indian
  light-industrial stock.
* Front office, production hall (1.7 met, high internal gain, hygiene
  ventilation), packing store. Three zones with genuinely different comfort
  physics, which is what makes single-set-point control wrong.

Visual: the zone plan from the top of `models/baseline.idf`.

## 3 — Architecture (criterion 4: agentic autonomy)

The three layers, and what each is for:

1. **EnergyPlus 25.2 in-process** via `libenergyplusapi`. 35 sensor handles read
   per timestep; nine `Schedule:Constant` actuators written in the same timestep,
   before the thermostat predictor runs.
2. **One tool registry, two consumers.** Eleven tools defined once, rendered as
   OpenAI/Ollama function schemas for the local model *and* as MCP `tools/list`
   for any external client. A local Qwen model and Claude Desktop drive the
   building through the identical interface.
3. **qwen2.5:3b in Ollama** — fully local, no API key, no GPU.

Say the phase-B line here: with `--ecm-pass` the agent stops adjusting
set-points and starts rewriting the `.idf` itself.

Visual: `docs/ARCHITECTURE.md` §1 and §2.

## 5 — Comfort is a constraint, not a trade-off (criterion 3)

This is the slide that separates a real result from a headline.

* Per-zone PMV limits by activity level: 0.8 office (1.05 met), 1.5 production
  hall (1.7 met), 1.1 packing (1.4 met). A single building-wide limit would be
  physically unreachable in the production hall and would make the metric
  meaningless.
* A **predictive PMV cap**: the safety layer stops the set-point where *that*
  zone would reach *its own* limit, linearising ISO 7730 about the measured
  operating point. Comfort is protected before it is breached, not repaired
  after.
* Applied in the engine to **every** brain — LLM, rules, baseline and external
  MCP clients. There is no path around it.
* Our PMV implementation matches the ISO 7730 worked examples to ±0.06 (tested).

Visual: `report/comfort.png`, plus the guardrail intervention count from
`results.json`.

## 6 — Prompt engineering and what the LLM actually contributes

Be straight about this; it is more persuasive than overclaiming.

Two measured failures and the fix:

1. General rules only → the model held 23–24 °C through an empty building all
   night. **Regression** against the baseline.
2. Resolved bands, plus guardrail feedback → the model echoed the correction text
   and never reached the evening setback. **−4.1%**. Still a regression.
3. Deterministic layer states a *recommended* set-point per zone per timestep;
   the model accepts, adjusts or overrides. **Positive savings, comfort
   improved.**

So: the arithmetic small models get wrong is done in code; the judgement is the
model's.

Then show the ablation, including the part that does not flatter us — a panel
will trust the rest of the deck more for it:

| | Total | HVAC | Peak-window |
|---|---|---|---|
| rules only | 8.79% lower | 12.23% lower | 7.63% lower |
| qwen2.5:3b in the loop | 5.52% lower | 7.69% lower | 8.00% higher |

qwen2.5:3b diverged from the recommendation on 79% of decisions and is *behind*
the rules it was advised by. Both arms preserve comfort. What is demonstrated is
the architecture — a real in-band loop, a structural comfort guarantee, and an
ablation exact enough to show a better model doing better behind one flag.

Visual: the "PER-ZONE SITUATION AND RECOMMENDED ACTION" prompt block, and the
divergence percentage from `results.json`.

## 7 — Latency management (criterion 1)

Measured: ~3.8 s prompt evaluation + ~2.4 s generation = 6.2 s per decision,
against a ~1 ms EnergyPlus timestep. A decision costs ~6000× a timestep.

Five mechanisms:

* decoupled clocks with a **latest-wins** snapshot slot — a slow decision is
  answered against fresh state, never a backlog;
* held actions **re-clamped every timestep**, so comfort tracks the building
  continuously between decisions;
* a hard wall-clock budget per decision, degrading to the deterministic policy —
  the run continues and the KPI records who decided;
* event-triggered cadence (occupancy flip, comfort breach, 1.5 °C move, 300 ppm
  move, peak-window transition);
* prompt-shape economies: terse tool schemas in the control scope, a compact
  state view, a stable prefix for KV-cache reuse, `keep_alive`, and a
  situation-fingerprint cache. Prompt cut from 2339 to ~1470 tokens.

Visual: the latency tiles from the dashboard.

## 8 — Robustness (criterion 1)

* 288 timesteps × 2 arms with zero severe EnergyPlus errors.
* Every callback body is wrapped: an exception inside an EnergyPlus callback
  crosses a C boundary and would abort the process, so a bad timestep degrades to
  "hold last action" instead of killing the run.
* `ToolRegistry.call` never raises — a bad tool call returns a message the model
  can read and retry.
* Hostile input tested through the guardrail: 45 °C set-points, NaN, `null`,
  words in numeric fields, inverted bands.
* 186 tests, green with no EnergyPlus, GPU or network.

## 9 — Phase B: the agent rewrites the building

```
propose → write .idf → simulate → FAIL → log digest → repair → retry
```

* Log handling: classify, fingerprint, rank, cap. A 40 000-line failure becomes
  ~600 characters that still name the offending object.
* Every generated variant is kept, failures included. On the submission run the
  model got it right first time (`cool_roof` + `glazing_upgrade`, exactly what the
  evidence pointed at), so say that plainly rather than implying the repair loop
  fired — the mechanism is in `ecm_report.json` and the transcript, and it is
  exercised by the test suite.
* ECM variants are scored under the *deterministic* policy against the same
  policy on the unmodified model, so a fabric change is never confounded with a
  control change.

Visual: the retrofit section of the dashboard, and the numbers from
`ecm_report.json`.

## 10 — Deliverables and how to reproduce

```bash
./scripts/setup.sh      # EnergyPlus, Chennai weather, Ollama + model
make run                # baseline + AI + retrofit pass
make serve              # live dashboard
make ablation           # rules-only arm, to isolate the LLM
```

Everything on disk per run: `savings.csv`, per-timestep telemetry for both arms,
every decision with rationale and latency, the exact IDFs simulated, the agent's
generated ECM variants, and EnergyPlus's own `eplustbl.htm`.

Close on the honest limitations rather than a superlative: adiabatic partitions,
a documented plant model rather than modelled refrigeration equipment,
representative rather than live grid signals, and a 3B model that needs the
deterministic advisory layer to beat a fixed schedule — with the same code ready
to run a larger model behind one flag.
